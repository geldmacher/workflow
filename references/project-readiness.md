# Project readiness

Use this guidance for commissioned setup or maintenance, or a concrete task-relevant prerequisite or feedback gap. Ordinary Workflow planning and execution inspect only the relevant project surface and reuse current evidence. Status and explanation do not initiate readiness work. A suitable existing setup needs neither a proposal nor a new format.

## Assess the useful feedback

Trace the human goal and authoritative project requirements to important user journeys and failure conditions. Inspect existing tests, evals, check scripts, project-local CI configuration, runtime prerequisites, and agent guidance. Establish how the executor can run the relevant checks and interpret failures. Distinguish instructions that guide the agent from observations that establish product behavior. Tests alone are not the specification; identify unresolved consequential acceptance choices.

Scale work to the project and assignment. Reuse established commands, harnesses, test data, and guidance locations. Propose evals when the relevant quality requires evaluation, with meaningful examples and assessment criteria; do not require an eval framework for every project. Identify short feedback routes during implementation and broader checks needed for acceptance. Record missing access or runtime prerequisites without claiming that configuration proves availability.

## Offer only concrete improvements

Use [setup-workflow](../skills/setup-workflow/SKILL.md) to establish the project basis and [maintain-workflow](../skills/maintain-workflow/SKILL.md) for existing setup. [workflow-doctor](../skills/workflow-doctor/SKILL.md) stays a task-level readiness inspection. A single verifier gap can go directly to [verification-work](../skills/verification-work/SKILL.md).

For setup or maintenance method assessment, proposals or selected work, read the [setup catalog](../skills/setup-workflow/references/catalog.md) and relevant entries. Offer one justified package with per-entry findings, coverage, benefit, changes, destinations and proof; allow subsets, revision or decline. Preserve matching existing assignments and carry selected, excluded, declined and unanswered scope through handoffs. Do not repeat unchanged offers, including in Light or Dark; explain materially changed needs. Optional additions do not block work. Missing necessary prerequisites limit dependent execution or completion claims; name adequate alternatives where available.

An accepted setup proposal that names a verifier's purpose, destination, coverage, and closing trial also authorizes that named verifier scope. Apply the [verification guidance](verification-work.md) and the appropriate creation or maintenance reference without a second offer or approval. Missing consequential scope still needs resolution. Do not create competing instructions or a second verifier to replace a suitable one.

## Implement and demonstrate the commissioned scope

Follow the applicable plan and phase assignment. Setup covers selected tests, evals, scripts, project-local CI, guidance and supported project-local subagent roles. Global host settings, machine-wide installation, external CI settings, production access and delivery need their own assignment. Local configuration does not prove remote enforcement or native role activation. Saving review-confirmed learning follows [learning](learning-work.md).

Put short, necessary entry guidance in existing project instructions and detailed procedures in appropriate project skills or documentation. Make when to check, exact runnable routes, relevant prerequisites, failure diagnosis, and remaining coverage clear. Keep existing locations and conventions; require no setup marker, registry, or new configuration format. Preserve unrelated work.

At implementation close, run the affected check routes on representative behavior. Where useful, exercise a controlled failing case in an isolated fixture to establish that the relevant defect is detected; preserve the agreed expected behavior. For commissioned verifier work, complete its required end-to-end trial when product and verifier are ready together. Retain actual commands, observations, and relevant side effects outside the tested workspace or in an authorized ignored evidence location. Clean only owned trial resources and confirm evidence survives cleanup.

After failure, distinguish product regression, broken check route and unavailable environment; correct only authorized work. Never weaken expectations to obtain success. Reassess affected evidence after changes. Report configured files, executed checks and remaining gaps separately. Failed or missing necessary proof prevents successful verification completion. Review compares selected methods, scope and current evidence read-only, without offering or repairing setup.
