# Project readiness

Use for setup, maintenance or concrete direction, prerequisite or feedback gaps. Ordinary work stays task-relevant. Status and explanation do not initiate readiness work.

## Establish and maintain direction

Setup always checks for a usable north star: whom the project serves, its purpose and intended benefit, decision principles and boundaries. Inspect descriptions, requirements and guidance; judge substance, not filenames. This is setup groundwork, not an optional playbook. Reuse a suitable definition without asking the user to reconfirm it.

For missing or vague direction, draft from known requirements. Ask about unknown users or benefit; leave them open until answered. Code behavior and silence cannot supply that decision. Save agreed content during commissioned implementation in the existing authoritative description, otherwise a short README section; link from agent guidance when needed. Reconcile conflicting sources with the user and maintain one definition rather than competing copies.

During Workflow use, assess relevant choices against this direction, the assignment and success criteria. Surface conflicts with their impact. A technical choice, task-specific exception or observed implementation does not establish a new project purpose. Explicit user decisions changing audience, purpose, benefit, principles or boundaries include the corresponding documentation update in the related implementation or correction, without another consent or learning phase. Update affected text and references; reusable lessons still follow [learning](learning-work.md).

Planning and Review stay read-only. Carry the decision, its basis, destination and pending update through handoffs, including Light/Dark; Review reports relevant conflicts or missed agreed updates. Maintenance checks actual files against explicit decisions, leaving suitable content unchanged, also on resume. Preserve declined and unanswered proposals without repeating unchanged offers. Missing direction limits only dependent decisions; bounded routine work needs no project-wide redefinition.

## Assess useful feedback

Trace the human goal and authoritative requirements to important user journeys and failures. Inspect tests, evals, check scripts, project-local CI, runtime prerequisites and guidance. Establish runnable checks and failure diagnosis. Agent instructions are not behavioral evidence; tests alone are not specifications. Resolve consequential acceptance choices.

Reuse suitable commands, harnesses, data and locations. Propose evals where quality needs evaluation, with examples and criteria. Identify short implementation feedback and broader acceptance checks. Configuration does not prove runtime access.

## Offer concrete improvements

Use [setup-workflow](../skills/setup-workflow/SKILL.md) to establish the basis and [maintain-workflow](../skills/maintain-workflow/SKILL.md) for existing setup. [workflow-doctor](../skills/workflow-doctor/SKILL.md) remains task-level inspection; individual verifier work goes to [verification-work](../skills/verification-work/SKILL.md).

For method assessment, proposals or selected work, read the [setup catalog](../skills/setup-workflow/references/catalog.md) and relevant entries. Offer one justified package with findings, coverage, benefit, changes, destinations and proof per entry; allow subsets, revision or decline. Preserve matching assignments and selected, excluded, declined and unanswered scope through handoffs. Do not repeat unchanged offers, including Light/Dark; explain materially changed needs. Optional additions do not block work. Missing necessary prerequisites limit dependent execution or completion claims; name adequate alternatives.

An accepted setup proposal naming a verifier's purpose, destination, coverage and closing trial authorizes that scope. Follow [verification guidance](verification-work.md) and its creation or maintenance reference without duplicate approval. Resolve consequential gaps; do not replace suitable instructions or verifiers with competing ones.

## Implement and demonstrate commissioned work

Follow the applicable plan and phase. Setup covers agreed direction, selected tests, evals, scripts, project-local CI, guidance and supported local subagent roles. Global settings, machine-wide installation, external CI, production and delivery need their own assignment. Files do not prove remote enforcement or native role activation.

Keep necessary entry guidance short, linking detailed procedures in existing skills or docs. Specify when to check, runnable routes, prerequisites, failure diagnosis and coverage limits. Preserve conventions and unrelated work; require no marker, registry or configuration format.

At implementation close, exercise affected routes on representative behavior. Where useful, demonstrate defect detection in an isolated failing fixture without weakening expectations. Complete commissioned verifier trials when product and verifier are ready together. Retain commands, observations and side effects outside the tested workspace or in authorized ignored evidence. Clean only owned resources and confirm evidence survives.

Distinguish product regressions, broken check routes and unavailable environments; repair only authorized work and reassess affected proof. Report configured files, executed checks and gaps separately. Failed or missing necessary proof prevents successful verification completion. Review assesses scope and evidence read-only, without offering or repairing setup.
