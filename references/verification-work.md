# Project verification

Use project verifiers when user-observable acceptance needs a running UI, CLI, service, side-effect boundary, or journey beyond established checks. Inspect repository guidance, existing checks and harnesses, and applicable verifiers, including `.agents/skills/verify-*` and `.cursor/skills/verify-*`. Reuse suitable coverage and keep usable existing locations and structures; static work already covered by established checks needs no verifier offer. Narrow multiple candidates by the planned product surface; ask only when a consequential ambiguity remains.

Doctor inspects without starting the product. Explain whether current verification is sufficient, a verifier is useful but absent, existing guidance has drifted, or missing access prevents a conclusion. These are explanations, not required status codes.

During planning, offer creation or maintenance only for a demonstrated gap. Explain the planned user journey, existing coverage, benefit, destination, affected features, and what the closing trial will prove. Let the human accept, decline, or revise the proposal. Only the explicitly accepted version enters implementation scope; silence is not consent. Preserve approval already given. After a decline, do not repeat the offer for that scope; retain the evidence gap and alternatives. Resolve any gap preventing agreed acceptance before finalizing the plan. For a new verifier use the nearest surface-owning `.agents/skills/verify-<surface>/` directory. An ambiguous owner or broader scope requires a decision.

When verifier work is accepted, read the [verification skill](../skills/verification-work/SKILL.md) and only its applicable creation or maintenance reference while remaining read-only. Put the accepted assignment, purpose, destination, coverage, applicable reference, and closing trial in the plan so a fresh native executor can implement it. Include evidence retention, failure reporting, and a separately commissioned Review of fit to both plan and implementation. Planning consent selects scope; the human implementation or correction instruction starts that work. An unaccepted suggestion grants no editing authority.

A usable verifier explains setup and launch, diagnosis, exercising behavior, expected observations and failure conditions, retained evidence, isolation, and cleanup. Concrete commands, selectors, data, and oracles must come from the repository. Do not leave placeholders or build a generic verification framework. New verifiers have skill frontmatter, a feature index, and files for agreed features; keep headings flexible and state uncovered behavior. Read [creation](../skills/verification-work/references/create.md) only for creation and [maintenance](../skills/verification-work/references/maintain.md) only for maintenance, including when planning that work. Existing suitable verifiers need no format-only migration.

Prefer local, fake, test, or dry-run boundaries for external effects; observe what they actually skip instead of trusting their names. Drive the real user path on the authorized surface and retain actions, resulting states, and relevant side effects. Store transient results outside the repository during Review; other phases may use an established ignored evidence location if authorized. Cleanup may remove only resources created by the current exercise. Existing resources and concurrent work are not cleanup targets. Clean owned residue after failed attempts too, and verify that evidence survives each cleanup.

The first required end-to-end trial belongs at implementation close, when product and verifier are ready together, not in a separate preliminary phase. Creation exercises at least one acceptance-relevant feature without replacing other necessary acceptance checks; maintenance exercises affected behavior, and `maintain full` exercises the agreed full map. Capture launch, readiness, drive, outcome, and cleanup evidence on the resulting working state. Missing runtime access leaves an untested result; failed or missing necessary proof prevents a successful verification completion claim.

When an oracle fails, report the observed product behavior rather than changing the expected outcome to accept it. Verifier maintenance changes only its authorized surface. In a separately commissioned Review, compare the verifier with the approved plan, actual implementation, and current evidence; for commissioned verifier changes, also check the accepted proposal and closing trial. Reusing a verifier without edits does not require creation or maintenance approval, but execution still follows the current assignment and host permissions. Inspect user paths, coverage, meaningful oracles, side effects, isolation, and evidence retention; perform necessary permitted rechecks. Never create or edit verifier files during Review. Stale guidance affecting acceptance is a finding; unrelated drift is a future task. Recheck affected observations after product or verifier changes. A structural inspection cannot establish live behavior, and a runtime check proves only what it actually observed.
