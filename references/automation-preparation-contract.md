# Auto-Planning and Root approval

`workflow_prepare` accepts exactly one goal or complete schema-3 Root plus `auto-gated` or `unattended-eligible`, a Route profile, revision zero, and an idempotency key. A supplied Root validates before duplicate resolution or any model call; schema 2, mixed, or incomplete schema 3 is rejected without migration. The key is bound to the exact source kind, Goal or raw Root hash, requested profile, and Route profile: an exact retry returns the same Preparation, while reuse for another request fails. Preparation state is external and expiring. Planning creates no Run.

For the goal/Root command form, resolve a `wp-*` to its exact complete Root and call `workflow_prepare` with a fresh key. For approval, fetch `root-ready`, then call `workflow_start` with its exact Preparation ID, displayed Root hash, current revision, and a fresh key.

The exact configured `planner` runs read-only in Plan mode with no setting sources and `fallback: deny`. It returns exactly one captured Cursor `CreatePlan`, at most three material Intent questions through the structured blocker tool, or technical failure. Plan and questions never coexist. Product decisions stop for `/plan-work`; only technical validation errors may resume the same Planner Agent within `planning_preflight_budget`. No model switch or headless interview is allowed.

The proposed Root must freeze the requested authorization boundary: allowed targets, risk ceiling, dependency and external-effect policy, local delivery boundary, Checks, and all Run budgets. `auto-gated` retains declared Slice gates and final local acceptance. `unattended-eligible` requests no planned post-Root gates, but the controller computes eligibility; a downgrade is visible and requires separate approval. Neither profile permits push, PR, merge, deploy, or automatic learning.

`root-ready` requires deterministic schema-3 validation and a complete Planner receipt covering requested, accepted, and observed model settings, SDK and harness versions/hashes, request and Agent IDs, usage, cost, duration, remap status, the input projection hash, and the controller-derived output projection hash. A supplied Root is exposed to the Planner only through its stable authoritative projection; its original opaque `extensions` value is restored outside the model afterward. Goal Planning has no input projection and strips Planner-invented extensions. Show the proposed Root, Preparation ID/revision, baseline, raw Root hash, authoritative projection hash, receipt/usage, and deterministic semantic diff before approval. Configuration, aliases, missing observations, or a remap are not attestations.

Only explicit `/auto-work <preparation-id> approve` authorizes the displayed Root hash. `workflow_start` must receive that exact hash and current Preparation revision. Under one repository lock it revalidates the unexpired, unused Preparation, Root, baseline, Route, policy, harness, budgets, receipts, and absence of another active Run; then it binds one consumed Preparation to one `plan_approved: true` Run. Root approval is never a later `/work-control` action, and a changed draft always needs a new approval.
