# Optional protected sealing contract

Fresh same-task Manual Review uses the local builder and does not require this contract. Protected sealing is a separate explicit opt-in boundary after or instead of a provisional Manual pair. After a local pair, `workflow_closeout` receives exactly two `seal_artifacts`: the immutable unprotected Evidence and Review bytes. Cursor validates that pair, binds it into the request hash, and supplies a protected single-use receipt bound to the exact Schema-6 Root, canonical workspace, current selection, invocation, repository state, and predecessor bytes.

The sealing path preserves an active valid Root across recoverable transport failures. Missing selection is reported separately from missing Root. Presentation defects or absent harness evidence create limitations; they do not invent Root-unavailable or alter Manual state.

After protected host binding, the project harness returns a generic PhaseResult with snapshots, changed paths, Check attestations, usage, and limitations. A local-pair sealing attempt appends `representation: seal` Delivery Evidence plus one Work Review only when every required Check is freshly verified and the Review is achieved; otherwise it returns no artifacts and leaves Manual status unchanged. Root-only formal Review may still remain provisional when attestations are missing. An unprovenanced local Review is accepted only as the direct non-authoritative predecessor of that sealed pair and never becomes a protected tip. Workflow never rewrites or upgrades already emitted Manual artifacts. A known failed required Check blocks delivery. A committed Cursor result uses `persistence_scope: native-review-invocation`; `handoff_persisted` describes only non-authoritative task transport. Sealing never deploys, publishes, pushes, merges, or learns.
