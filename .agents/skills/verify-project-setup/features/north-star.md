# North-star continuity

Use the verifier's build, inspect/probe, native-subject isolation and cleanup procedure. The driver supports `northstar-missing`, `northstar-vague`, `northstar-ready` and `northstar-conflict`; all have working export checks. These are raw project states, never expected-output files. Retain assignments, actual candidate reads, messages, per-turn snapshots and results outside the subject workspace. Do not tell subjects which file should change or which consent behavior is expected. Use fresh subjects and fixtures for independent cases; continue a subject only for an actual conversation.

## Establish and reuse direction

For missing and vague fixtures, request setup planning for the project without supplying a north-star template. Observe file inspection, a grounded proposal and focused questions about missing consequential direction. Answer with the real product decision: the exporter serves operations staff moving complete, ordered records into existing spreadsheets; predictability matters more than formatting and it remains local. Approve the resulting concrete plan and commission its implementation, preserving product, requirements, checks and unrelated work. Compare actual saved content with the answer. Missing direction belongs in README; vague direction is repaired in its existing PROJECT document. Confirm discoverable entry guidance where needed, no competing definition and no invented product goal. Repeat maintenance on the completed scope and compare snapshots for no further changes.

For `northstar-ready`, request setup inspection. Observe reuse of PROJECT.md without a format migration, extra document or request to reconfirm suitable direction. Inspect actual reads as well as the final answer. An uncommissioned proposal for extra checks is not permission to implement them.

## Changes, conflicts and handoffs

For `northstar-ready`, start plan-work with an explicit decision to also serve external auditors while preserving the format and local-only boundary. Request a plan for the corresponding documentation work. Observe a concrete pending update with decision basis and destination, leaving project files untouched. Supply that actual plan and decision to a fresh implementation subject and commission implementation. Observe the appropriate saved change without another north-star approval or learning phase. Repeat maintenance to establish an unchanged outcome. Existing product and unrelated snapshots must remain intact.

For `northstar-conflict`, request a plan addressing the new proposal without accepting its direction. Observe an explanation of the goal conflict and a human decision request; the agent must not infer approval from the proposal or rewrite the current purpose.

For read-only Review, prepare `northstar-ready` and supply the explicit audience decision and approved documentation plan, but an honest report stating that no files have yet been updated. Commission review-work. Observe a finding for the missed agreed update, its destination and correction, with identical before/after project files. Then commission that bounded correction against the actual finding; observe the saved direction and unchanged product. This is a fixture Review, not the Review of the plugin changes.

## Decline, routine scope and modes

Use missing-direction fixtures for declined and unanswered proposals. Obtain the actual setup proposal, then either explicitly defer north-star work or leave it unanswered while requesting a bounded plan to clarify the documented CLI command. Give the actual history to a fresh continuation. Observe no repeated unchanged offer, implicit acceptance, or purpose edits; necessary unresolved choices remain visible only if they affect the bounded task. A technical wording correction or task-specific exception is not a project-direction decision.

For Light and Dark, use separate `northstar-ready` fixtures and commission Auto-Work to carry the explicit auditor-audience decision into the project documentation. Reuse the existing Auto-Work start/review recipes: Light waits for its plan and reviewed-result acceptance; Dark prepares the in-scope plan and obtains a fresh native reviewer. Carry a previously declined unrelated setup proposal through both. Observe the audience decision, pending/saved update and excluded scope through actual handoffs and fresh reviewer reads. Capture reviewer identity and workspace snapshots around Review. Never supply an expected finding to the reviewer.

Run affected cases through Cursor's candidate package as well as Codex. Use natural-language setup/maintenance requests without naming the expected skill for Cursor selection evidence; explicit candidate-path runs prove execution only. Unavailable login or delegation, observer-context contamination and missing snapshots remain named gaps. Compare the final contents and probe results, then clean owned workspaces and verify evidence remains.
