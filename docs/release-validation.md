# Workflow 5 validation boundaries

Repository validation covers Schema 5, Config/Policy 2, Protocol 5, deterministic Evidence, append-only indexed state, workspace-unattested recovery closeout, Lean/Full selection, active-Root resolution, Replan lineage, provisional acceptance, legacy read-only compatibility, Strategy chaining, authority, Dirty Baseline, task recipes, evidence calibration, model Pools, Verification Profiles, the inheritance and Schema-5 `CreatePlan` guards, MCP Roots, bundle parity, 10% context headroom, links, and the canonical release surface. Focused offline coverage gates require at least 80% lines and 70% branches for Root authority, the Schema-5 `CreatePlan` guard, Capability Receipts, release surface, Worker Adapter, and state/handoff indexes; generated bundles are excluded.

`release-surface.json` remains the canonical Cursor `runtime_paths` inventory used by Plugin hashing and isolated installed-copy startup. The target builder creates a separate Codex inventory in its package. Package verification requires complete copied surfaces without symlinks; every relative path resolves inside its selected plugin root. Codex leakage checks reject host-specific SDK/API-key identifiers and every Controller-only MCP tool name.

It does not by itself prove live Cursor model availability, hook enforcement, or actual inherited child-model identity. Following [Cursor's documented workaround for unenforced `subagentStart` denial](https://forum.cursor.com/t/subagentstart-hook-deny-is-not-enforced/166143/7), `preToolUse` is the primary Task override block. `subagentStart` compares the reported Child with the captured parent, while `subagentStop` and `postToolUse` distinguish a displayed denial from an executed and returned Child. Only Cursor can resolve and execute inheritance. Live smokes with two different Cursor-selected models must inspect the hook log and actual agent tree. A result returned despite Deny is recorded as `deny-not-enforced`; the result may still be used after separate fachliche verification, but the affected run is not exact-model-qualified. SDK enforcement, Marketplace installation, OS sandbox behavior, keychain access, real UI driving, and production dependency safety likewise require the separate certification runbook and an exact Capability Receipt Schema 4.

Repository tests verify provider-neutral parent switching, omitted/`inherit` requests, concrete override denial, equality and mismatch, missing and uncorrelated attestations, parallel/idempotent events, denial bypass observation, non-Workflow isolation, and incident privacy. Artifact Schema 5 and the authoritative `wp/de/wr/cp` chain remain unchanged.

Until every hard capability is positive, supervised remains Shadow Mode. Autonomous remains disabled per Qualification Key. Missing live proof is reported as unavailable; it is never promoted from repository tests or reviewer opinion.

`npm run release-check` is reproducible, offline, and inference-free. Registry audit, installed-copy/Marketplace smoke, and paid Cursor certification are separate gates. A fresh High/Critical production finding blocks certification until a minimal dependency fix or explicit hash-bound risk acceptance; an unavailable external check is never reported as passed.

Repository validation can prove both bundles, eight Codex skills, the five-tool Manual MCP, pure Hook decisions, migration behavior, and byte-preserving interoperability. It cannot prove that a personal marketplace accepted the copied package, that the user trusted the current Hook hash, that a newly started Codex task discovered every component, or that the host enforced every live event. Those remain a fresh-task local smoke; no new Codex automation certification is implied because the Codex target has no automation profile.

Live smokes, paid model use, and registry or network access require separate explicit human approval and a stated cost limit before execution.
