# Project guidance

Use when an arriving contributor or agent cannot find reliable prerequisites, commands or acceptance routes. Inspect existing README, project instructions, scoped rules, skills and docs before adding a new location. Working conventions need no format migration.

## Put each instruction where it is useful

Keep the always-loaded entry short: necessary project constraints, change-to-check routing and links to detail. Use host-supported scoped rules only when a directory or task genuinely needs different guidance; verify their scope and precedence. Put longer procedures in task-oriented docs or an appropriate skill. Keep one maintained source for each procedure and link to it instead of copying commands across files.

Describe the reader's goal, prerequisites, exact execution context, commands, expected results, failure diagnosis and relevant cleanup. Derive paths and commands from the project. Separate instructions from historical evidence, and mark unavailable checks honestly. Do not store secrets, transient logs or an exhaustive framework manual in always-loaded guidance.

Possible artifacts are a README addition, concise AGENTS guidance, a scoped rule or a testing/development guide. For DDEV, explain that PHP checks use the container and link the actual project check command; template changes can point to the affected page recipe. Names such as `docs/testing.md` are examples, not required layout.

## Prove and maintain

Read the combined guidance as a fresh executor, check links and follow the affected runnable route. Confirm scoped rules are discoverable by the intended host when their behavior matters. Maintenance removes stale command references and reconciles duplicate or conflicting sources against current project truth. A wording cleanup alone does not prove the documented product behavior.
