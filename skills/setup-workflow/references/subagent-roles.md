# Subagent roles

Use only for a concrete recurring need for specialized multi-step work, separate context or independent judgment. Short single-purpose actions usually fit a command or skill. Inspect existing roles, actual host/version capabilities and project configuration; do not infer native delegation from a filename or generic plugin support.

## Configure a bounded project role

Name its trigger, assignment, required inputs, output and evidence, read/write scope, stopping conditions and handoff. Reuse project instructions and skills instead of copying them into the role. Identify who owns edits and how the parent waits for and assesses results. Avoid overlapping writers and unlimited fan-out. A reviewer must inspect a fixed state without editing it and remain separate from its implementer.

Use the active host's supported project-local format and location, preserving existing entries. Confirm the format against installed capabilities or authoritative current host documentation when uncertain. Cursor may use project agent Markdown and Codex project agent TOML, but cross-host compatibility is not assumed. No global configuration, feature enablement or model installation follows from selecting this entry. Inherit model/reasoning settings by default; a role's task does not justify inventing a model override.

Describe the benefit and execution cost before including the role in the setup package. An accepted role assignment includes its project destinations and a bounded delegation trial. Prompt instructions describe intended scope; use available host restrictions and distinguish them from enforced isolation. Role creation does not commission future production actions or change Workflow review authority.

Possible artifacts are a focused project role and a link to its reusable procedure. A repository with frequent independent schema checks could use a read-only schema reviewer returning findings with source evidence; it should not silently repair the schema or start unrelated review work.

## Prove and maintain

Confirm the host discovers the saved role, then observe an actual delegated task, child identity, relevant instruction use, result handoff and file effects. Also check a neighboring task does not require the role. A successful generic child spawn does not prove that the configured role was used. Missing discovery or delegation leaves that proof open; offer an adequate supported alternative without inventing host settings. Maintenance rechecks triggers, tool access, role overlap, inherited settings and continued benefit after host or project changes.
