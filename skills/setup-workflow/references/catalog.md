# Project setup playbooks

Setup and maintenance share these methods. Start from project requirements and actual gaps, using this catalog to narrow the relevant references. Read only those needed to assess the project, explain an offer, or perform selected work. Exclude clear non-matches from the catalog; do not load all entries to justify omissions. Reading is not selection. These methods neither select Engineering playbooks nor commission another Workflow phase.

| Entry | Use when | Reference |
|---|---|---|

| `behavior-tests` | Requirements or regressions lack repeatable behavior checks. | [Behavior tests](behavior-tests.md) |

## Offer a useful combination

For a concrete gap, offer one recommended package of one or more entries. For each, connect the project finding and current coverage to its benefit, proposed change, destination and closing proof. Name overlap and shared artifacts once. Add alternatives only for a meaningful tradeoff. Allow accepting the package, choosing a subset, revising it or declining all; in German use "Empfohlen" and "Nein, nicht machen". A suitable setup needs no offer or format migration.

Only the accepted scope enters the plan. A matching existing assignment already selects its named work; do not ask again because it lacks playbook IDs. A bare skill invocation starts inspection and a proposal, not implementation. Acceptance of a plan containing the explicit package can select that package; silence or a general Auto-Work mode cannot. Preserve purpose, destinations, coverage and closing trial for included verifier work and use verification-work without another offer.

Carry selected, excluded, declined and unanswered scope through task handoffs. Do not repeat an unchanged offer in later phases, including Light or Dark; reopen only a materially changed need with its reason. Necessary missing proof remains visible even when an optional addition is declined. Maintenance compares the relevant standards with current requirements and actual files; unchanged suitable work is a successful no-change result.

## Apply the selected standards

Adapt examples to the repository's actual versions, interfaces and tools. Use existing suitable mechanisms before adding dependencies or artifacts. These are quality criteria, not a requirement to install every tool or produce every file. Report configured artifacts, executed checks and remaining limits separately. The working agreement and project-readiness guidance retain authority over phases, evidence and external effects.
